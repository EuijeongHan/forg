# forG 제품 개편안 — 공시 알림 봇에서 신뢰 가능한 공시 모니터링 서비스로

- 작성일: 2026-07-27
- 기준: `main` eac710f
- 현재 운영: 로컬 Docker 단일 인스턴스
- 대상 사용자: 여러 상장사를 지속적으로 모니터링하는 기관 애널리스트·운용역·RA

## 1. 결론

forG는 기능을 더 붙이기 전에 제품의 중심을 다시 정해야 한다.

> **내 관심기업의 중요한 공시에서 달라진 숫자와 다음 일정을 놓치지 않게 한다.**

전체 시장 탐색, 영구 키워드 두 벌, 키워드 동기화, AI 코멘트는 핵심이 아니다. 사용자가
처음부터 이해해야 하는 개념을 줄이고 다음 세 가지 행동만 선명하게 만든다.

1. 관심기업을 등록한다.
2. 중요한 공시가 오면 핵심 사실과 변경점을 확인한다.
3. 오늘 놓친 공시와 앞으로의 일정을 다시 본다.

## 2. 현재 제품의 문제

### 2.1 조회와 설정이 뒤섞여 있다

현재 명령은 다음과 같이 동작한다.

- `/today`: 전체 시장의 오늘 중요 공시
- `/mytoday`: 관심기업의 오늘 전체 공시
- `/keyword`: `/today`에 영구 적용되는 키워드 설정
- `/mykeyword`: `/mytoday`에 영구 적용되는 키워드 설정
- `/settings`: 두 키워드의 동기화

사용자는 공시를 보려는데 먼저 “조회 범위”, “영구 필터”, “동기화 상태”를 배워야 한다.
또한 `/keyword`라는 이름은 결과 조회처럼 보이지만 실제로는 숨은 상태를 변경한다.
이전에 저장한 필터 때문에 `/today` 결과가 달라지는 것도 알아차리기 어렵다.

### 2.2 제품의 핵심과 시작 화면의 우선순위가 다르다

서비스의 핵심은 관심기업 자동 알림이지만 `/start`는 전체 명령을 같은 위계로 나열한다.
전체 시장 조회와 키워드 설정이 관심기업 등록만큼 중요해 보인다.

### 2.3 AI가 가치의 중심처럼 보인다

사용자에게 진짜 중요한 것은 빠른 감지, 정확한 숫자, 정정 전후 변화, 향후 일정이다.
“AI가 해석한 주목 포인트”는 정확성·비용·법률 리스크를 동시에 늘린다. 정형 API가 있는
공시는 AI 코멘트보다 결정론적 카드가 우선이어야 한다.

### 2.4 운영 장애가 사용자에게 그대로 노출된다

현재 운영은 로컬 Docker인데 문서에는 Railway가 프로덕션으로 적혀 있다. 동일 Telegram
토큰으로 로컬 프로세스를 중복 실행할 수 있고, Telegram 초기화가 한 번 타임아웃되면 앱
전체가 종료된다. Docker 자동 재시작과 운영/개발 환경 분리도 없다.

“중요 공시를 놓치지 않는다”는 서비스에서 침묵 중단은 가장 먼저 제거해야 할 실패다.

### 2.5 측정할 사용자 행동이 거의 없다

Telegram은 메시지 읽음 여부를 제공하지 않는다. 현재 데이터로는 발송 성공과 일부 버튼
클릭만 알 수 있다. 사용자가 알림을 유용하게 봤는지, 너무 많다고 느끼는지, 어떤 공시
유형이 가치 있었는지 판단하기 어렵다.

### 2.6 구현 로드맵이 사용자 검증보다 앞서 있다

현재 조사 문서에는 설문지와 인터뷰 질문은 있지만 실제 응답과 인터뷰 기록은 없다.
따라서 팀 협업, KIND 연동, 웹 대시보드, 결제 같은 후속 단계는 확정 로드맵이 아니라
검증할 가설로 취급한다. 먼저 실제 누락 사례와 현재 확인 절차를 재구성해야 한다.

## 3. 제품 원칙

1. **관심기업 우선**: 전체 시장 피드는 보조 기능이다.
2. **사실 우선**: 정형 숫자와 원문을 AI 서술보다 먼저 보여준다.
3. **변화 우선**: 공시 한 건의 요약보다 이전 값에서 무엇이 바뀌었는지 보여준다.
4. **보이는 상태**: 사용자가 모르는 영구 필터를 만들지 않는다.
5. **알림과 조회 분리**: 알림 규칙은 `/alerts`, 조회 조건은 해당 조회 명령에 둔다.
6. **신뢰성 우선**: 새 기능보다 누락·중복·중단 방지를 먼저 해결한다.
7. **추천 금지**: 호재·악재, 목표가, 매수·매도 판단을 만들지 않는다.

## 4. 새로운 사용자 흐름

### 4.1 첫 화면

`/start`에는 전체 명령 목록 대신 가치 제안과 네 개의 버튼만 둔다.

```text
관심기업의 중요한 공시를 놓치지 않게 도와드립니다.
핵심 숫자·정정된 내용·향후 일정을 DART 원문과 함께 보여드려요.

[＋ 관심기업 추가]   [오늘 내 공시]
[시장 주요 공시]     [알림 설정]
```

긴 사용법은 `/help`로 옮긴다. 투자 관련 짧은 고지와 약관 링크는 하단에 유지한다.

### 4.2 명령 체계

| 명령 | 새 역할 |
|---|---|
| `/today` | 내 관심기업의 오늘 중요 공시. 버튼으로 전체 공시 전환 |
| `/today 유상증자` | 내 관심기업의 오늘 중요 공시를 이번 조회에서만 필터 |
| `/market` | 전체 시장의 오늘 중요 공시 |
| `/market 유상증자` | 전체 시장 중요 공시를 이번 조회에서만 필터 |
| `/watchlist` | 관심기업 조회·추가·삭제 |
| `/alerts` | 영구 알림 규칙과 전달 방식 설정 |
| `/digest` | 오늘 리캡 조회 또는 리캡 시간 설정 |
| `/help` | 전체 사용법 |

삭제 대상:

- `/keyword`
- `/mykeyword`
- 키워드 동기화 설정

기존 사용자를 위해 `/mytoday`는 한동안 `/today` 별칭으로 유지한다. `/keyword`와
`/mykeyword`는 즉시 오류를 내지 않고 새 사용법을 한 번 안내한 뒤 단계적으로 제거한다.
DB의 기존 키워드 컬럼은 첫 배포에서 삭제하지 않고 롤백 기간 동안 보존한다.

### 4.3 조회용 필터와 알림용 설정

조회용 키워드는 일회성이다.

```text
/today 전환사채
/market 감사보고서
```

알림 설정은 자유 문자열보다 공시 유형 버튼을 우선한다.

```text
알림 받을 유형
[✅ 자금조달] [✅ 자사주] [✅ M&A]
[✅ 감사]     [❌ 지분변동] [✅ 정정]

전달 방식
[✅ 즉시 알림] [❌ 18:30 리캡] [둘 다]
```

이렇게 하면 “키워드가 어디에 적용되는가”를 사용자가 기억할 필요가 없다.

## 5. 새로운 공시 카드

알림은 짧은 제목과 긴 AI 문단 대신 다음 순서로 구성한다.

```text
🏢 A사 · 012345
전환사채 발행결정 · 16:42

발행금액       150억원
전환가액       3,250원
전환청구 시작  2027-07-01
자금용도       운영자금 100억원

정정 공시라면
❗ 발행금액 100억원 → 150억원

다음 일정
⏰ 전환청구 시작까지 D-340

[DART 원문] [변경 보기] [확인]
[오류 신고]
```

표시 원칙:

- 정형 API 값은 카드에 직접 표시한다.
- 정형 API가 없는 공시만 AI 요약을 보조적으로 쓴다.
- AI 생성 여부와 검증 가능 여부를 구분해 표시한다.
- “주목 포인트”, “호재”, “악재” 같은 평가 표현은 쓰지 않는다.
- 핵심 숫자를 계산할 근거가 없으면 0으로 표시하지 않고 생략한다.
- 조회 목록 상단에는 범위·중요도·날짜·검색어·총건수를 항상 표시한다.

## 6. 기능 우선순위

### 반드시 살릴 기능

- 관심기업 자동 알림
- DART 정형 API 우선
- 사용자별 중복 방지
- 원문 링크
- 공시 유형별 핵심 숫자 카드
- 정정 전후 비교
- 향후 일정

### 보조 기능으로 내릴 기능

- 전체 시장 중요 공시
- 자유 키워드 검색
- AI 서술형 요약

### 당분간 만들지 않을 기능

- 종목 추천·호재/악재 판정·주가 예측
- 범용 공시 챗봇
- 팀 협업 기능
- KIND 상시 수집
- 결제와 티어 게이팅
- Next.js 대시보드

사용자 인터뷰와 실제 사용량으로 필요성이 확인되기 전에는 후순위로 둔다.

## 7. 실행 로드맵

### Phase 0 — 운영 신뢰성 복구 (3~5일)

목표: 사용자가 아무 응답도 받지 못하는 상태를 자동으로 복구한다.

- 운영 문서를 로컬 Docker 기준으로 교정
- 개발용 토큰과 운영용 Telegram 토큰 분리
- 운영 컨테이너는 항상 하나만 실행
- `restart: unless-stopped`와 Docker healthcheck 추가
- Telegram 초기화에 제한된 재시도·지수 백오프 적용
- DB 준비 완료 후 앱을 시작하도록 healthcheck 연결
- 운영 DB 포트는 호스트 외부에 공개하지 않음
- 운영용 Compose에서 소스 볼륨 마운트 제거
- `docker compose up -d --build` 한 명령으로 배포
- DB 백업·복구 절차 문서화
- 스케줄러에 `max_instances=1`, `coalesce=True`를 명시해 중첩 폴링 방지
- `/health`에 마지막 성공 폴링·마지막 DART 수집 시각과 처리 건수 추가
- DART 수집 결과를 `success`·`empty`·`partial`·`error`로 구분
- 전일 대상 공시와 실제 발송 기록을 대조하는 일일 누락 점검 추가
- `Watchlist(chat_id, corp_code)` DB 유니크 제약과 migration 추가
- PostgreSQL에 Alembic을 실제 적용하는 CI와 correction·verification 테스트 연결
- 개인정보처리방침의 Railway 문구를 실제 로컬 Docker·PostgreSQL 운영 구조로 교정
- 약관·개인정보처리방침을 GitHub 저장소 주소가 아닌 사용자용 정식 URL에 게시
- 봇 안에 개인정보·관심기업 데이터 삭제 요청 경로 마련

완료 조건:

- 컴퓨터 또는 Docker 재시작 후 봇이 자동 복구된다.
- Telegram 일시 타임아웃 한 번으로 프로세스가 영구 종료되지 않는다.
- 동일 토큰을 쓰는 두 poller를 운영 절차상 만들지 않는다.
- 정상적인 무공시와 수집 실패를 운영 로그·헬스체크에서 구분할 수 있다.
- 일일 대조에서 대상 공시 누락과 중복을 자동으로 탐지한다.

### Phase 0A — 문제 검증 (Phase 0과 병행, 1주)

목표: 구현된 기능 목록이 아니라 실제로 반복되는 공시 업무 문제를 확인한다.

- 기관 애널리스트·RA·운용역 8~12명 인터뷰
- 최근 실제 누락·지연·정정 오인 사례를 시간 순서로 재구성
- 현재 사용하는 DART·메신저·엑셀·사내 시스템과 확인 책임 조사
- 외부 Telegram에 관심기업을 등록할 수 있는지 컴플라이언스 확인
- 핵심 숫자 카드·정정 비교·미확인 재알림 중 어떤 기능이 행동을 바꾸는지 검증
- 5명 내외의 4주 파일럿 사용자 모집

완료 조건:

- 가상의 선호가 아니라 최근 실제 사례 8건 이상을 확보한다.
- 파일럿 사용자가 현재 공시를 확인하는 데 걸리는 기준 시간을 측정한다.
- Telegram 사용이 불가능한 조직의 비율과 이유를 기록한다.

### Phase 1 — 명령과 첫 화면 단순화 (3~5일)

목표: 처음 쓰는 사람이 설명 없이 관심기업을 등록하고 오늘 공시를 본다.

- `/start`를 네 개의 행동 버튼으로 교체
- 조회 서비스를 `scope`·`important_only`·`query`·`date`가 명시적인 단일 경로로 통합
- `/today`를 관심기업 중심으로 변경
- `/market` 신설
- 조회 명령 인자로 일회성 필터 지원
- `/keyword`, `/mykeyword`, 동기화 UI 폐기 안내
- `/watchlist`에서 추가·삭제를 버튼으로 통합
- 여러 기업명·종목코드를 붙여넣는 관심기업 일괄 등록
- 목록 20건 초과 페이지네이션
- 결과 상단에 범위·중요도·날짜·검색어·총건수 표시
- “오늘 공시 없음”과 “검색 조건 결과 없음”을 구분
- `/help`로 상세 설명 이동

완료 조건:

- 신규 사용자가 2분 안에 기업 등록과 첫 조회를 끝낸다.
- `/keyword`와 `/mykeyword`의 차이를 설명할 필요가 없다.
- 저장된 필터 때문에 조회 결과가 예상과 달라지는 일이 없다.

### Phase 2 — 신뢰 가능한 이벤트 카드 (4~6일)

목표: AI 문장보다 정확한 숫자 카드가 제품의 기본 출력이 된다.

- 이벤트 정규화 플래그를 전환사채·유상증자부터 제한적으로 활성화
- `DisclosureEvent` 정식 Alembic migration과 인덱스 추가
- 기존 정형 카드와 새 이벤트 카드의 실데이터 대조
- fixture 검증 후 기존 출력과 shadow 비교하고 단일 테스트 사용자부터 확대
- 결정론적 검증 계층을 발송 직전에 연결
- 정형 공시의 AI 추가 코멘트 제거
- 검증 실패 시 카드와 원문만 발송
- `확인` 버튼과 발송·확인 시각 저장
- “오류 신고” 버튼과 검증 로그 저장

완료 조건:

- 지원 유형의 핵심 숫자가 DART 정형 응답과 일치한다.
- 검증 실패가 알림 전체를 침묵시키지 않는다.
- 사용자 신고를 접수번호와 함께 재현할 수 있다.

### Phase 3 — 정정 전후 비교 (4~6일)

목표: 사용자가 원본을 다시 읽지 않고 무엇이 바뀌었는지 확인한다.

- `DisclosureRelation` 정식 Alembic migration과 인덱스 추가
- 실제 DART 정정공시 fixture로 연결 규칙 검증
- 금액·수량·일정 등 major 변경만 알림 상단에 표시
- 확정할 수 없는 연결은 “추정 연결”로 표시
- 중요한 변화가 없는 정정은 리캡으로 보낼지 사용자 테스트

완료 조건:

- 실제 정정 사례에서 이전 값과 이후 값이 정확히 표시된다.
- 잘못 연결된 원본 비율을 측정한다.
- 같은 정정공시가 중복 알림되지 않는다.

### Phase 4 — 알림 설정과 리캡 (4~6일)

목표: 알림량을 줄이면서 놓치지 않는 방식을 사용자가 선택한다.

이 단계는 파일럿에서 알림 과다 또는 리캡 수요가 실제로 확인될 때만 시작한다. 초기에는
복잡한 조건식 대신 공시 유형과 전달 방식만 저장한다.

- `AlertRule` 테이블과 migration
- 공시 유형별 알림 토글
- 즉시 알림·18:30 리캡·둘 다 선택
- 이미 저장된 이벤트 카드로 리캡 생성
- 기존 사용자는 현재 즉시 알림을 기본값으로 유지

완료 조건:

- 알림 설정 변경이 조회 결과에는 영향을 주지 않는다.
- 리캡 때문에 공시별 LLM 호출이 늘지 않는다.
- 사용자별 발송량과 설정 변경률을 측정한다.

### Phase 5 — 타임라인과 웹 판단 (사용 데이터 확보 후)

다음 조건을 만족할 때만 REST API와 웹 화면을 착수한다.

- 실제 파일럿 사용자 10명 이상
- 4주 이상 지속 사용 데이터
- Telegram에서 해결되지 않는 탐색·비교 요구가 반복 확인됨
- 정정 비교와 일정 데이터 품질이 안정됨

웹을 만든다면 우선순위는 기업 타임라인, 정정 비교, 향후 일정, 알림 설정 순이다.

### 6주 MVP 경계

- **1주차**: Phase 0 운영 복구와 Phase 0A 인터뷰를 병행한다.
- **2주차**: Phase 1을 배포하고 5명 파일럿을 시작한다.
- **3~4주차**: 전환사채·유상증자부터 Phase 2 카드를 적용하고 정확도를 대조한다.
- **5~6주차**: 실제 정정 사례에 Phase 3을 제한 적용하고 파일럿 결과로 다음 한 단계를 고른다.

Phase 0~2가 MVP의 필수 범위다. Phase 3은 검증 실험이며, Phase 4~5는 파일럿 데이터로
수요가 확인될 때만 시작한다.

## 8. 기술 구조 변화

```text
DART 수집
  → Disclosure 원본 저장
  → 정형 이벤트 정규화
  → 변화·일정 계산
  → 사용자 AlertRule 판정
  → 카드 렌더링과 검증
  → Telegram 즉시 알림 / 리캡
```

역할 분리:

- `dart.py`: DART 입출력
- `events/`: 숫자·날짜 정규화, 비교, 일정 계산
- `services/`: 조회·관심기업·알림 규칙·리캡
- `verification/`: 발송 전 결정론적 검증
- `notifier.py`: 렌더링된 메시지 전송
- `bot.py`: 버튼과 명령 I/O만 담당

현재 프로세스 메모리인 `disclosure_cache`에 의존하지 않고 접수번호로 DB에서 공시를
다시 조회할 수 있게 해야 한다. 다중 인스턴스 전환 전까지 Redis는 필요 없다.

현재 중복 방지는 강하지만 Telegram 발송 성공 후 DB 커밋 전에 프로세스가 죽으면 같은
알림이 다시 발송될 수 있다. 다중 인스턴스나 강한 전달 보장을 도입하기 전에는
`delivery/outbox` 테이블로 발송 시도·성공·확인을 분리한다.

스키마 변경은 `create_all()`에 기대지 않는다. 필요한 migration을 먼저 적용하고, 충분한
운영 검증 뒤에는 migration 실패 시 기동을 중단하는 방식으로 전환한다.

## 9. 측정 지표

북극성 지표는 **중요 공시 확인 보장률**이다.

> 업무시간에 발생한 관심기업의 대상 중요 공시 중 정상 발송되고 15분 안에 사용자가
> `확인`을 누른 비율

Telegram의 자연스러운 읽음 여부가 아니라 제품 안의 명시적 확인 행동만 측정한다.

### 신뢰성

- DART 폴링 성공률
- 공시 접수부터 알림 발송까지 p50·p95 지연
- Telegram 발송 성공률
- 중복 알림 수
- 연속 실패 후 자동 복구 시간
- 컨테이너 재시작 횟수와 원인

### 품질

- 정형 API 적중률
- 지원 카드 필드의 DART 원본 일치율
- 검증 warning·fail 비율
- 정정 원본 연결 성공률과 오연결률
- 사용자 오류 신고율

### 제품

- `/start` 후 관심기업 등록 완료율
- 첫 관심기업 등록까지 걸린 시간
- 사용자별 관심기업 수 중앙값
- `/today`, `/market`, 원문 보기, 변경 보기 사용 횟수
- 7일·30일 재사용률
- 즉시 알림·리캡 선택 비율
- 공시 유형별 “확인” 버튼 비율

Telegram은 읽음 여부를 제공하지 않으므로 “메시지 열람률”을 측정했다고 표현하지 않는다.

### 파일럿 목표치

- DART 일일 대조 기준 대상 중요 공시 누락 0건
- 중복 발송 0건
- 공시 접수부터 발송까지 p95 3분 이내
- 지원 정형 카드의 핵심 숫자 불일치 0건
- 잘못 연결된 정정공시 0건
- 불필요하다고 평가된 알림 10% 이하
- 신규 사용자가 5분 안에 관심기업 3개 이상 등록
- 파일럿 5명 중 4명 이상이 4주 후에도 사용
- 기존 방식 대비 핵심 내용 파악 시간 50% 이상 단축

소규모 파일럿에서는 비율만 보지 않고 분모와 모든 실패 사례를 함께 기록한다.

## 10. 파일럿 운영

1. 인터뷰 대상 중 기관 실무자 5명을 파일럿으로 모집한다.
2. 설명 없이 관심기업 등록과 오늘 공시 조회를 시킨다.
3. 막힌 지점, 이해하지 못한 명령, 불필요한 알림을 기록한다.
4. 4주 동안 발송량·확인 버튼·재사용을 측정하고 2주차에 중간 점검한다.
5. 인터뷰에서는 기능 선호보다 실제로 놓친 공시 사례와 필요한 대응 시간을 묻는다.
6. 4주 후 유지·삭제·후순위 기능을 결정한다.

가장 먼저 검증할 질문:

- 전체 시장 피드가 실제 업무에 필요한가?
- 중요 공시만 즉시 받고 나머지는 리캡으로 충분한가?
- 정정 비교가 AI 요약보다 더 자주 쓰이는가?
- Telegram에 관심기업을 등록하는 것이 회사 정책상 가능한가?

## 11. 바로 실행할 작업 묶음

첫 번째 배포는 기능을 많이 넣지 않는다.

1. Docker 자동 복구와 Telegram 초기화 재시도
2. `/start` 행동 버튼
3. `/today` 관심기업 중심, `/market` 전체 시장
4. 일회성 조회 필터
5. 기존 키워드 명령 폐기 안내
6. 운영·제품 지표의 최소 로그

이 배포가 안정된 뒤 이벤트 카드와 정정 비교를 순서대로 연결한다.
